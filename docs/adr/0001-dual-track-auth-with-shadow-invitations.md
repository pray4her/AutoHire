# 双轨认证:开放注册(Better Auth)与邀请链接并存,账号轨走影子邀请

平台原本只有邀请链接一种准入方式:token 即身份,无账号体系。我们决定**保留邀请链接轨原样不动**,同时新增**开放注册**:任何人可用邮箱+密码注册账号(注册时邮箱验证码验证)并发起申报。账号轨用 Better Auth 实现(Prisma adapter,新增 user/account/session/verification 表,纯增量),邮件通道复用现有 nodemailer;ops 密码登录与审计看板认证维持手写实现,不迁入 Better Auth。

账号轨用户没有邀请,而 `Application.invitationId` 必填且唯一,全链路(17 状态机、材料、初审、ops 档案、邮件回退)都建立在此结构上。与其把 `invitationId` 改可空并回归全链路,我们选择:**账号注册时系统自生成一张影子邀请**(email 绑注册邮箱,token 永不用于链接登录),申报照旧挂在邀请上,现有代码零改动。

## Considered Options

- **仅邀请制 + 账号激活**(邀请绑邮箱,链接仅作一次性激活):保留门禁最严,但拒绝了开放申报口的业务诉求,被否。
- **开放注册 + `invitationId` 可空 + 新增 userId 外键**:语义最诚实,但所有按邀请鉴权/查询的代码都要兼容空值,回归面大,被否。
- **注册即生成真邀请可走链接登录**:两套身份在同一用户身上重叠,双轨名存实亡,被否。
- **Auth.js / 自研**:邮箱 OTP、会话、限流需自拼,无优势,被否。
- **强制手机验证或手机为主标识**:需签约短信服务商(资质+模板报备以周计),安全收益不成比例,被否;邮箱为主标识,手机号保持可选。

## Consequences

- 同一人可能同时拥有链接轨与账号轨两份申报:**不合并、不拦截**,重复甄别属 ops 审核职责;若未来泛滥,再加"疑似重复"软标记(纯增量)。
- `ExpertInvitation.email` 由死字段变为账号轨的真实绑定字段。
- 申报后续流程(材料、初审、状态查询)两轨完全合流,共用同一 Application 链路。
- 未来若要给账号轨加手机验证,Better Auth phoneNumber 插件可增量叠加。
